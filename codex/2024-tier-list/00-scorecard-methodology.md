# Subclass Scorecard Methodology (2024)

**สถานะ**: กติกากลางสำหรับไฟล์ `<class>-subclass-scorecard-2024.md` ทุกคลาส — เขียนไว้ที่นี่ที่เดียว แต่ละไฟล์รายคลาสลิงก์กลับมาแทนการ copy เนื้อหาซ้ำ (ดู [§ การใช้งานในไฟล์ต่อคลาส](#การใช้งานในไฟล์ต่อคลาส) ท้ายไฟล์)

---

## 7 Axis

ทุก subclass ให้คะแนน 7 แกน แกนละ 0-10:

1. **Damage** — พลังทำลายล้างในคอมแบต
2. **Control** — ลดประสิทธิภาพศัตรู (CC/debuff/บังคับผลลัพธ์)
3. **Support** — เสริมพวกพ้อง (ฮีล/บัฟ/utility ให้ทีม)
4. **Survivability** — เอาตัวรอด (HP/AC/resist/หนี)
5. **Action Economy** — ความคุ้มค่าต่อ action/resource ที่เสีย **รวมทั้ง 2 มิติ**: (ก) ต้นทุนต่อครั้งที่ใช้ (เสีย action/BA/reaction ไหม หรือฟรี) และ (ข) ความยั่งยืนตลอดวัน (ใช้ได้กี่ครั้ง/วัน ฟื้นเร็วแค่ไหน — subclass ที่ "จ่ายตูมทีเดียวแล้วแห้งทั้งวัน" จะได้คะแนนต่ำกว่าที่ sustain ได้สม่ำเสมอ แม้ magnitude ต่อครั้งจะสูงกว่า)
6. **Utility** — exploration/social/downtime นอกคอมแบต
7. **Versatility** — ใช้ได้ทุกสถานการณ์/ทุกช่วงเลเวล ไม่ผูก build ตายตัว

**Overall Tier ของทั้ง subclass เป็นดุลยพินิจแยกต่างหาก ไม่ใช่ค่าเฉลี่ยของ 7 axis** — อาจไม่ตรงกับค่าเฉลี่ยราย axis เสมอไป (เช่น subclass ที่แรงด้าน Damage มากด้านเดียวแต่ D ทุกด้านอื่น อาจได้ Overall Tier ต่ำกว่าที่ค่าเฉลี่ยบอก เพราะเล่นได้แค่ role เดียว)

## ขอบเขต edition — ใช้กฎ 2024 เท่านั้น

เว็บนี้เล่นกฎ **2024 เป็นหลักเสมอ** มีผลต่อการเขียนเหตุผล/ให้คะแนนดังนี้:

- **Subclass ที่มีทั้งเวอร์ชัน 2014 และ 2024 (reprint)** → ให้คะแนนและเขียนเหตุผลจากกลไก/ตัวเลขของ **เวอร์ชัน 2024 เท่านั้น** เพิกเฉยเวอร์ชัน 2014 เดิมไปเลย ไม่ใช่แค่ "หยิบอันที่ดีกว่ามาเขียน" — ถ้าจะพูดถึง 2014 ได้แค่ในวงเล็บเปรียบเทียบท้ายประโยคเท่านั้น (ดูกติกาเหตุผลด้านล่าง)
- **Subclass ที่ไม่มี reprint 2024 (2014-only orphan)** → ยังต้องรวมไว้ในตารางเหมือนเดิม ให้คะแนนจากกลไก 2014 เวอร์ชันเดียวที่มี (เพราะเป็นตัวเลือกเดียวที่มีในโปรเจกต์) กำกับ 🕰️ เสมอตาม legend ของโปรเจกต์
- นี่คือ scope เดียวกับที่ `class-subclass-index.md` / `00-sub-class-overview-tier-list-2024.md` ใช้อยู่แล้ว (ดู `dedupeSubclassesByName` ใน generator scripts ที่ preferข้ 2024 เมื่อมีทั้งคู่) — ระบุไว้ที่นี่ให้ชัดว่ากติกาเดียวกันนี้ใช้กับการเขียนเหตุผลราย axis ด้วย ไม่ใช่แค่ตอนเลือกว่าจะ list subclass ไหนเข้าตาราง

## Class Chassis Baseline — subclass ไม่ได้เริ่มจาก 0 ทุก axis

**ปัญหาของกติกาเดิม**: ให้คะแนนจากฟีเจอร์ของ subclass ล้วนๆ ทำให้ subclass ที่เน้น niche เฉพาะทาง (เช่น Abjurer เน้น survivability) โดนกด axis อื่น (Damage) เป็น 0 ทั้งที่ตัว **class แม่เอง** ก็ยังเล่น role นั้นได้อยู่ดี (Wizard ทุก subclass ร่าย Fire Bolt ได้เหมือนกันหมด ไม่ว่าจะเลือก subclass ไหน)

**หลักการ**: คะแนนแต่ละ axis ของ subclass = **Baseline ของ class** (ความสามารถจาก chassis ล้วนๆ ไม่นับ subclass) **บวก** ส่วนที่ subclass เสริมเพิ่มจริง — subclass ไม่มีทางได้คะแนนต่ำกว่า baseline ของ class ตัวเอง เว้นแต่ subclass นั้นตัดทอนความสามารถนั้นออกไปจริงๆ ด้วยกลไกเฉพาะ

### วิธีทำ

ก่อนให้คะแนน subclass ตัวแรกของ class ใดๆ ต้องเขียน **ตาราง Class Baseline** ไว้ที่หัวไฟล์ `<class>-subclass-scorecard-2024.md` (ก่อนตาราง tier แรก) — floor ตัวเลข 0-10 ต่อ axis ของ **class เปล่าๆ ไม่มี subclass** (นับเฉพาะสิ่งที่ทุก subclass ของ class นี้ได้เหมือนกันหมด: spell list, extra attack, save proficiency, skill proficiency ฯลฯ) เขียนครั้งเดียว ใช้ร่วมกับทุก subclass ของ class นั้นตลอดทั้งไฟล์

```markdown
## Class Baseline (Wizard)

| Axis | Baseline | เหตุผล |
|---|---|---|
| Damage | 5 | Full spell list มี damage cantrip/spell ให้เลือกเพียบ (Fire Bolt ฯลฯ) ไม่ต้องพึ่ง subclass [M:2/4] [R:2/3] [B:1/3] |
| Control | ... | ... |
| ... | ... | ... |
```

(ตัวเลขในตัวอย่างนี้เป็นแค่ตัวอย่างโครงสร้าง ไม่ใช่ค่าจริงที่ล็อกไว้ — ต้องวิเคราะห์จริงตอนเริ่มทำไฟล์ Wizard)

### กติกาการใช้ Baseline ตอนให้คะแนนรายแกน

1. คะแนนของ subclass ใน axis ใดๆ **ต้อง ≥ Baseline ของ class เสมอ** ยกเว้น subclass ตัดทอน/ห้ามความสามารถนั้นออกไปจริงๆ ด้วยกลไกเฉพาะ (ต้องระบุกลไกที่ตัดทอนชัดเจนในเหตุผล ถ้าจะให้คะแนนต่ำกว่า baseline — เช่น subclass บังคับห้ามร่ายคาถา attack เพื่อแลกของอย่างอื่น)
2. **subclass ที่ไม่ได้เสริมอะไรเพิ่มใน axis นั้นเลย → คะแนน = Baseline เป๊ะๆ** (ไม่ใช่ baseline − 1) ระบุในเหตุผลว่าไม่มีฟีเจอร์เสริมด้านนี้จาก subclass เอง คะแนนมาจาก class baseline ล้วนๆ — **ห้ามให้ 0** ถ้า baseline ของ class ไม่ใช่ 0
3. subclass ที่เสริมเพิ่มจาก baseline → คะแนน = baseline + ส่วนที่เสริมจริง เขียนอธิบายทั้งสองส่วนรวมกันในประโยคเดียว (ไม่ต้องแยก tag baseline vs เสริมใน `[M:x/4]` ให้ M/R/B สะท้อนคะแนนรวมสุดท้ายตามปกติ)
4. Baseline เขียนครั้งเดียวต่อ class ไม่ต้องคำนวณใหม่ทุก subclass — subclass ทุกตัวอ้างอิงเลขเดียวกันได้เลย

### ตัวอย่าง (Before → After, สมมติ Wizard baseline Damage = 5/10)

❌ เดิม: **Damage 0/10 (D)** — "ไม่มีดาเมจเสริมเลย"

✅ ใหม่: **Damage 5/10 (B)** — "Wizard chassis มี spell list เต็มที่มี damage cantrip/spell ให้เลือกเพียบ (Fire Bolt, Fireball ฯลฯ) โดยไม่ต้องพึ่ง subclass — Abjurer เองไม่มีฟีเจอร์เสริม damage เพิ่มจาก baseline นี้เลย [M:2/4] [R:2/3] [B:1/3] (คะแนน = Wizard baseline ล้วนๆ)"

## M/R/B scoring (ที่มาของคะแนน 0-10 แต่ละ axis)

แต่ละ axis คะแนนรวม 0-10 มาจาก 3 มิติย่อย บวกกัน:

| มิติ | ช่วงคะแนน | ตอบคำถาม |
|---|---|---|
| **Magnitude (M)** | 0-4 | ผลลัพธ์แรงแค่ไหนตอนทำงาน (ตัวเลขดิบ: ดาเมจ, HP, DC, ระยะ, จำนวนเป้าหมาย ฯลฯ) |
| **Reliability (R)** | 0-3 | ใช้ได้บ่อย/แน่นอนแค่ไหน (auto-hit หรือต้องพึ่ง save/roll, จำกัดกี่ครั้ง/วัน, ฟื้นเร็วแค่ไหน) |
| **Breadth (B)** | 0-3 | ครอบคลุมสถานการณ์กว้างแค่ไหน (ใช้ได้ตลอดเกมหรือเฉพาะบางสถานการณ์/บาง build) |

**M + R + B = คะแนนรวม (0-10)** แปลงเป็นเกรด:

| Grade | คะแนนรวม |
|---|---|
| S | 9-10 |
| A | 7-8 |
| B | 5-6 |
| C | 3-4 |
| D | 0-2 |

## กติกาการเขียน "เหตุผล" ต่อ axis

**หลักการ**: เหตุผลต้องอธิบาย**กลไกจริง**ที่ทำให้ได้คะแนนนี้ (ตัวเลข/trigger/เงื่อนไข/ความถี่ที่จับต้องได้) — **ไม่ใช่แค่บอกว่า subclass นี้ดีขึ้นหรือแย่ลงเทียบกับ edition ก่อนหน้า** การเทียบ edition ใส่ได้แต่เป็นแค่ข้อมูลเสริมท้ายประโยค ไม่ใช่เหตุผลหลัก

**Format**:

```
<คำอธิบายกลไกจริง 1-3 ประโยค ระบุตัวเลข/เงื่อนไข/ความถี่ที่ทำให้ได้คะแนนนี้> [M:x/4] [R:y/3] [B:z/3]
```

**กติกา**:

1. **ต้องมีตัวเลข/เงื่อนไขที่จับต้องได้อย่างน้อย 1 อย่าง** ทุกครั้งที่คะแนน > 0 — เช่น dice/HP ที่ได้, DC, ระยะ, จำนวนเป้าหมาย, จำนวนครั้ง/วัน หรือต่อ rest, action cost (action/BA/reaction/free) ห้ามเขียนกว้างๆ แบบ "แรงมาก" หรือ "ใช้ได้ดี" เฉยๆ
2. **ปิดท้ายด้วย `[M:x/4] [R:y/3] [B:z/3]` เสมอเมื่อคะแนน > 0** — ผลรวม x+y+z ต้องเท่ากับคะแนนที่ประกาศในคอลัมน์ Score พอดี ถ้าคะแนน = 0/10 (ไม่มีกลไกด้านนั้นเลย) เขียนสั้นได้แบบเดิมโดยไม่ต้องมี tag เช่น "ไม่มีฟีเจอร์ควบคุมเลย"
3. **การเทียบ edition เก่า (2014→2024) เป็นได้แค่ประโยคเสริมท้ายสุด** ใส่ในวงเล็บ เช่น `(เทียบกับ 2014: เดิมต้องพึ่ง reaction ถึงจะเติม ward ได้)` — ห้ามเป็นประโยคเดียวของทั้งเหตุผล เพราะไม่บอกกลไกจริงว่าทำไมถึงได้คะแนนนี้
4. **ความยาว**: 1-3 ประโยคก่อน tag พอ ไม่ต้องเวิ่นเว้อ แต่ต้องมีตัวเลข/เงื่อนไขจริงเสมอ — ถ้าอธิบายกลไกครบแล้วสั้นกว่านี้ได้ก็ไม่ต้องยืดเพิ่ม

### ตัวอย่าง (Before → After)

**Abjurer, axis Survivability, 7/10 (A)**

❌ เดิม (บอกแค่ว่าดีขึ้น ไม่บอกกลไก):
> Arcane Ward (temp-HP shield) เติมง่ายขึ้นในเวอร์ชัน 2024 + โบนัส saving throw ต้านคาถา

✅ ใหม่ (กลไกจริง + ตัวเลข + M/R/B breakdown):
> Arcane Ward ให้ temp HP เท่า 2×Wizard level + Int mod ตอนได้ subclass (lv2) เติมเต็มอัตโนมัติทุกครั้งที่ร่าย abjuration spell lv1+ ไม่จำกัดจำนวนครั้ง/วัน กันดาเมจได้ก่อนโดน HP จริงเสมอตราบมี ward เหลือ แต่ยังเป็น temp HP ธรรมดา ไม่ resist/ไม่หนี และต้องมี abjuration spell เตรียมไว้ถึงจะเติมได้ [M:3/4] [R:3/3] [B:1/3] (เทียบกับ 2014: เดิมต้องพึ่ง reaction ถึงจะเติม ward ได้ 2024 ตัดเงื่อนไขนี้ทิ้ง)
